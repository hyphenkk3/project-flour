### Operational response runbook

Use this as a decision sequence if a Production failure occurs. It is operational guidance only; do not perform destructive recovery steps without a separate, explicit owner decision.

1. **Declare and contain.** Record UTC and Malaysia timestamps, affected route/workflow, sanitized request/error IDs, and the first observed symptom. Check Supabase and Vercel service status and current deployment identity using read-only views. If errors are recurring (including statement timeout or aborted-transaction symptoms), stop release activity immediately. Do not retry refunds, payments, checkout, or migrations blindly; do not broaden permissions or disable RLS.
2. **Separate application from database symptoms.** If the database remains healthy and the issue follows an application deployment, preserve logs and deployment identity. An application rollback may be considered only to a known READY deployment with an independently verified artifact and explicit release-owner authorization. Do not assume such a candidate exists: the current rollback-candidate listing was blocked. Application rollback does not undo database changes.
3. **If a migration is in progress or has failed, stop.** Do not rerun it blindly. Establish whether its transaction committed and inspect the migration version and affected objects read-only. If atomic rollback is proven and the old application remains healthy, keep the old application and escalate the sanitized error. If commit state or partial effects are uncertain, do not attempt a dump restore or hand-written rollback; require a reviewed, data-preserving forward repair plan and owner authorization.
4. **If existing workflows fail after a committed schema change, preserve records.** Pause further release actions, capture the failing operation and request IDs, and use the known-good application artifact only if it is verified and authorized. Leave additive schema in place unless a reviewed rollback proves safe for newly created records. Prefer a compensating forward fix over dropping columns, constraints, functions, or new refund records.
5. **If data recovery is required, protect transactions after the recovery point.** Never restore the October 14 snapshot over live Production. First verify the provider's current recovery point, timestamp, retention, target-isolation options, and expected data loss window. A point-in-time restore to an earlier time can omit subsequent orders/payments/refunds; identify and preserve those transactions before any cutover. Restore into an isolated target where supported, validate aggregates and critical workflows, and obtain explicit owner approval before any production routing or replacement decision.
6. **Recover the whole service, not only PostgreSQL.** Track database schema/data and privileges, Auth identities/configuration/passkeys, Storage metadata and object bytes, managed extensions/jobs, secrets/provider settings, and the application artifact/configuration as separate recovery components. Verify each component before declaring service restored.
7. **Resume only after owner-led validation.** Verify current order visibility and status transitions, payment/refund history, Fresh Pick stock/reservations, staff login and passkeys, catalogue/pricing/photos, reports, and storefront checkout using safe read-only checks or isolated synthetic tests.
