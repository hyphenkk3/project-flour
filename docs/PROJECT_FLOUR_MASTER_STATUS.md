## Production refund permission audit — 16 October 2026

**VERIFIED by read-only catalog inspection:** The Supabase management connection identified the target as `project-flour-prod`, reference `cuowwlduhxxifmpvpltt`, PostgreSQL 17.6. Catalog reads ran in a transaction whose `transaction_read_only` setting was `on`. No table rows were queried and no database objects or permissions were changed.

- `public.refunds` is owned by `postgres`; RLS is enabled, `FORCE ROW LEVEL SECURITY` is off. The ACL grants table-level SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, and MAINTAIN to `anon`, `authenticated`, `service_role`, and `postgres`; no column-level ACL entries were present. `supabase_admin` also has effective access through its administrative privilege.
- The only refund policy found is permissive `SELECT` for `authenticated` with `USING (true)`. No INSERT, UPDATE, DELETE, or ALL policy exists. `anon` has no refund policy. Thus ordinary `anon` and `authenticated` INSERT/UPDATE/DELETE statements are denied by RLS despite their table ACL grants. Their read access is likewise constrained by RLS (authenticated has the SELECT policy; anon does not).
- **Confirmed direct-write risk:** `anon` and `authenticated` also have `TRUNCATE` table privilege. PostgreSQL TRUNCATE is not governed by RLS, so any SQL execution path that can issue it under either role could bypass refund RPCs and erase the table. The ordinary Supabase REST table API does not provide a general SQL/TRUNCATE endpoint, but the catalog grant is still an unsafe privilege to preserve. In addition, `service_role` has all table DML grants and `BYPASSRLS`, so it can directly insert/update/delete/truncate without RPC validation. `postgres` also has `BYPASSRLS` and owns the table; `supabase_admin` is superuser. No inspection established whether deployed backends use service-role direct refund-table writes.
- Existing `record_overpayment_refund` and `cancel_and_refund_paid_fresh_pick` signatures remain executable by `authenticated`, `service_role`, and `postgres`, not `anon`. `record_payment_correction` has the same execute-role set. The refund aggregate helper `order_refunds_total(uuid)` is executable by `PUBLIC`, `anon`, `authenticated`, `service_role`, and `postgres`; this is pre-existing and was not changed. The new V1 RPCs are absent in Production at audit time.
- The approved draft SHA-256 remains `fc010e4ff5719ed526a0bf580c72c70f5876088a3232d0cc33c92744863ce725`. It leaves current table ACLs and RLS untouched; it revokes broad execute defaults on each new RPC and grants `authenticated` for general/Fresh Pick recording, and `authenticated` plus `service_role` for the metadata-aware overpayment wrapper. It does not change any existing RPC ACL.

**ASSESSMENT:** Preserving all current grants in the draft is **not recommended** because it preserves `TRUNCATE` for `anon` and `authenticated`, which RLS cannot prevent. Minimum permission correction before release: revoke direct `INSERT`, `UPDATE`, `DELETE`, and `TRUNCATE` on `public.refunds` from `anon` and `authenticated`; the current policies already prevent the first three, while removing TRUNCATE closes the RLS bypass. This should not affect SECURITY DEFINER refund RPCs owned by `postgres`, but must be included in the Production-specific draft and re-rehearsed before approval. `service_role` remains a trusted privileged bypass; whether to revoke its direct DML/TRUNCATE requires a separate backend call-site review so existing trusted workflows are not broken. The current audit cannot establish whether that key is used for direct refund writes.

No permissions were changed. At the time of that audit the original draft hash matched; it was subsequently corrected and rehearsed as recorded below.
